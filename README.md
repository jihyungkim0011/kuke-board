# 대규모 게시판 시스템 트러블 슈팅 및 아키텍처 최적화 가이드

이 문서는 **대규모 데이터와 트래픽을 처리하는 분산 마이크로서비스 환경**에서 발생하는 여러 기술적 병목과 이를 해결하기 위한 구체적인 **트러블 슈팅 과정 및 최적화 아키텍처 패턴**을 다룹니다.

---

## 1. 대용량 데이터 페이징 성능 개선 및 조회 최적화 (MySQL)

### 문제 상황: 1,200만 건 대용량 테이블에서의 페이징 지연
*   **원인:** 전통적인 `LIMIT M OFFSET N` 방식을 사용하여 뒤 페이지(예: 50,000번 페이지, OFFSET 1,499,970)를 조회할 때 쿼리 수행 시간이 **4.16초**까지 급격히 증가하는 심각한 성능 저하가 발생했습니다.
*   **분석:** MySQL InnoDB 엔진의 **Clustered Index(PK)**와 **Secondary Index(보조 인덱스)** 구조적 특성 때문입니다. 
    *   **Clustered Index**는 리프 노드에 실제 행 데이터(Row Data)를 물리적으로 정렬하여 가집니다.
    *   **Secondary Index**는 리프 노드에 인덱스 컬럼 데이터와 함께 데이터에 접근하기 위한 포인터(PK)만 가집니다.
    *   `LIMIT 30 OFFSET 1499970` 쿼리 실행 시, 보조 인덱스 트리와 클러스터형 인덱스 트리를 오가며 **버려질 앞선 1,499,970건의 데이터 블록(디스크 I/O)까지 무의미하게 전부 디스크에서 읽어 들이고 버리는(Skip)** 비효율적인 인덱스 스캔을 수행하기 때문입니다.

### 해결 단계 1: 커버링 인덱스(Covering Index)와 조인 결합
*   **개념:** 쿼리에 필요한 모든 컬럼이 보조 인덱스(Secondary Index)에만 존재할 경우, 클러스터형 인덱스(디스크 데이터 블록)에 접근하지 않고 인덱스 노드의 정보만으로 조회를 완료하는 **커버링 인덱스 기법**을 도입했습니다.
*   **최적화 쿼리:**
    ```sql
    -- 인덱스: idx_board_id_article_id (board_id ASC, article_id DESC)
    SELECT * 
    FROM (
        SELECT article_id 
        FROM article
        WHERE board_id = 1
        ORDER BY article_id DESC
        LIMIT 30 OFFSET 1499970
    ) t 
    LEFT JOIN article on t.article_id = article.article_id;
    ```
*   **결과:** 서브쿼리 내부에서 `idx_board_id_article_id` 보조 인덱스만을 스캔하여 (`Extra: Using index` 확인) 30건의 `article_id`를 0.2초 만에 먼저 빠르게 선별합니다. 이후 딱 선별된 30건에 대해서만 PK 기반의 클러스터형 인덱스 단건 조회(`PRIMARY`)를 수행하여 전체 데이터를 채워줍니다. 성능이 **4.16초에서 0.2초로 약 20배 개선**되었습니다.

### 해결 단계 2: 극단적 대용량 페이징의 한계 극복, No-offset (Cursor) 기반 페이징
*   **추가 한계 발견:** 커버링 인덱스를 적용하더라도, 300,000번 페이지(OFFSET 8,999,970)와 같이 극단적으로 깊은 오프셋 조회 시 보조 인덱스 자체를 스캔하는 비용으로 인해 쿼리가 **1.5초** 이상 지연되는 한계가 여전히 존재했습니다.
*   **근본적 해결 (No-offset):** 무한 스크롤 환경의 특성을 살려 마지막으로 조회한 데이터의 식별자(`last_article_id`)를 기준점(Cursor)으로 넘기는 No-offset 방식을 적용합니다.
*   **최적화 쿼리:**
    ```sql
    -- 2페이지 이상 조회 시 (마지막 ID 기반 범위 필터링)
    SELECT * 
    FROM article
    WHERE board_id = {board_id} 
      AND article_id < {last_article_id}
    ORDER BY article_id DESC 
    LIMIT 30;
    ```
*   **결과:** B+Tree 복합 인덱스에서 기준점(`last_article_id`)을 로그 시간 $O(\log N)$ 내에 찾은 후 연속된 30건만 스캔하므로, **뒤 페이지에서도 전체 데이터 규모와 무관하게 일정한 조회 속도(0.00초 대)를 유지**합니다.

### 해결 단계 3: 대용량 데이터 Count 쿼리 최적화
*   **문제:** 전체 페이지 번호를 보여주기 위한 `SELECT COUNT(*)` 쿼리가 1,200만 데이터 환경에서 인덱스를 타더라도 **1.28초**가 소요되는 지연이 발생했습니다.
*   **최적화 1 (페이지 수 제한 및 서브쿼리 활용):** 사용자가 1~10페이지에 있을 때는 다음 버튼 노출을 위해 최대 301개의 데이터 유무만 확인하면 됩니다. 전체 카운트 대신 특정 한계치까지만 카운트하는 범위 제한 서브쿼리를 적용했습니다.
    ```sql
    SELECT COUNT(*) 
    FROM (
        SELECT article_id 
        FROM article 
        WHERE board_id = {board_id} 
        LIMIT 301 -- 현재 활성화할 최대 개수만 보조 인덱스로 확인
    ) t;
    ```
    *   **결과:** 실행 시간이 **1.28초에서 0.07초로 단축**되었습니다.
*   **최적화 2 (Pre-aggregation):** 실시간 카운트 비용을 0으로 만들기 위해, 별도의 카운트 전용 테이블(`board_article_count`)을 신설하고 게시글 생성/삭제 시 비관적 락 기반 트랜잭션 내에서 동기적으로 수치를 증감시키는 비정규화 데이터 캐싱 구조를 적용했습니다.

## 2. 좋아요 서비스 동시성 제어 및 분산 트랜잭션 제어 (MySQL)

### 문제 상황: 동시성 유실(Lost Update) 및 분산 트랜잭션 병목
*   **원인:** 다수의 사용자가 동시에 단일 인기 게시글에 좋아요 버튼을 클릭했을 때, 각 트랜잭션이 동일한 좋아요 수 레코드를 경쟁적으로 조회 후 수정하면서 **데이터가 서로 덮어씌워져 좋아요 수가 누락되는 동시성 문제**가 발생했습니다.
*   **아키텍처 제약:** 마이크로서비스 분산 데이터베이스 환경에서 좋아요 상세 테이블(`article_like`)과 좋아요 수 합계 테이블(`article_like_count`)이 물리적으로 서로 다른 샤드(Shard)에 구축될 경우, 동기화를 위해 느리고 복잡한 분산 트랜잭션(2PC 등)이 강제되어 전체 장애 유발 요인이 됩니다.

```text
[요청 1] ──► [샤드 A: article_like 생성] ┐
                                       ├─► (분산 트랜잭션 필요: 성능 저하 및 블로킹 유발)
[요청 2] ──► [샤드 B: like_count 증가 ] ┘
```

### 해결 단계 1: 샤드 키 일치를 통한 로컬 트랜잭션 보장
*   **설계 변경:** 분산 데이터베이스 환경이지만, 두 테이블의 **샤드 키(Shard Key)를 모두 게시글 ID(`article_id`)로 일치**시켰습니다.
*   **효과:** 특정 게시글의 좋아요 데이터와 카운트 데이터가 **같은 물리 데이터베이스 노드(Shard)에 저장**되므로, 복잡한 분산 트랜잭션 없이 **로컬 트랜잭션 범위에서 원자성을 확보**했습니다.

### 해결 단계 2: 비관적 락(Pessimistic Lock) vs 낙관적 락(Optimistic Lock) 최적화
동시성 문제를 해결하기 위해 두 가지 방식의 락킹(Locking) 구조를 모두 설계 및 구현하여 트레이드오프를 조정했습니다.

1.  **비관적 락 - 원자적 갱신 방식 (UPDATE 식):**
    *   **구현:** 
        ```sql
        UPDATE article_like_count 
        SET like_count = like_count + 1 
        WHERE article_id = {article_id};
        ```
    *   **분석:** 데이터베이스의 로우 레벨 독점 락(Exclusive Lock)을 짧게 획득하고 별도의 조회 쿼리도 필요하지 않아, 좋아요가 몰리는 상황에서 지연을 줄일 수 있습니다.
2.  **비관적 락 - 명시적 락 획득 방식 (SELECT FOR UPDATE 식):**
    *   **구현:** `SELECT ... FOR UPDATE`로 엔티티를 영속 영역에 먼저 가져와서 락을 걸고 연산 후 수정합니다. 락 점유 시간이 길어져 병목이 증가하나, 비즈니스 검증 로직이 자바 애플리케이션 내에 객체 지향적으로 풍부하게 필요한 경우에 적절합니다.
3.  **낙관적 락 (JPA @Version 활용):**
    *   **구현:** 엔티티에 `version` 컬럼을 적용하여 동시 수정 시점에 버전 일치 여부를 매번 조건절에 확인합니다.
        ```sql
        UPDATE article_like_count 
        SET like_count = {new_count}, version = version + 1 
        WHERE article_id = {article_id} AND version = {current_version};
        ```
    *   **분석:** 락을 전혀 유지하지 않으므로 트랜잭션 지연이 적지만, 버전 불일치 시 트랜잭션 실패 예외가 발생하므로 애플리케이션 영역에서 롤백 및 복잡한 재시도(Retry) 매커니즘을 동반해야 합니다. 좋아요 충돌 빈도가 매우 드문 일반적인 게시글 환경에서 가장 적절합니다.

## 3. 초고속 조회수 집계 및 분산 락 기반 어뷰징 방지 (Redis)

### 문제 상황: 쓰기 트래픽 병목 및 조회수 조작(어뷰징)
*   **원인:** 조회수(View Count)는 단순히 조회가 발생할 때마다 쓰기 연산(I/O)이 발생하는 'Read-intensive write' 특성을 지닙니다. 게시글 조회 요청마다 매번 MySQL 디스크 I/O를 직접 발생시키면 성능이 급격히 저하됩니다. 또한, 동일 사용자가 새로고침을 반복해 조회수를 빠르게 조작하는 어뷰징이 발생했습니다.

### 해결 단계 1: Redis In-memory 아키텍처 및 10분 주기 분산 락(setIfAbsent) 적용
*   **구조:** 빠른 I/O 속도와 데이터 자동 삭제(TTL)를 지원하는 Redis Cluster 인프라를 활용하고, 단일 스레드(Single Thread)로 동작하여 명령어의 원자성이 보장되는 강점을 활용합니다.
*   **어뷰징 방지 정책:** 사용자별(ID)로 특정 게시글에 대해 **"10분에 한 번만 조회수가 1 증가한다"**는 원자적 분산 락 메커니즘을 수립했습니다.

```text
[Client 게시글 조회] 
         │
         ▼
[Redis: setIfAbsent(Key: articleId+userId, TTL: 10분)]
         │
         ├──► [성공(True)] ──► "첫 조회수 증가 허용" ──► Redis INCR 조회수 갱신
         │
         └──► [실패(False)] ─► "10분 내 재조회 차단" ─► 조회수 증가 요청 무시
```

*   **구현 로직:**
    1.  사용자 요청 시 Redis의 `setIfAbsent`를 통해 `key = articleId + userId`로 분산 락(TTL = 10분) 획득을 시도합니다.
    2.  처음 시도하여 `True`를 받으면 락 점유에 성공한 것이므로 Redis에 키가 등록되며 동시에 조회수 수치를 1 증가(INCR) 시킵니다.
    3.  10분 내에 연이어 요청하면 이미 점유된 락이 존재하므로 `False`를 받고, 조회수 갱신 없이 즉시 무시하고 요청을 성공 종료합니다.

### 해결 단계 2: Redis 휘발성 차단을 위한 MySQL 벌크 배치 백업
*   **영속성 문제:** Redis는 완전 휘발성 인메모리 저장소이므로 서버 전원 중단 시 조회수가 모두 증발하는 리스크가 있습니다.
*   **해결:** 실시간 일관성이 꼭 필요하지 않은 조회수의 특성을 고려해 **"개수 단위 백업" 전략**을 적용했습니다. Redis에서 개별 게시글 조회수 누적이 `100`단위에 도달할 때마다 비동기 이벤트 스트림으로 MySQL(`article_view_count`)에 100건 단위의 벌크 머지 백업을 병렬 수행하여 영속성을 확보하고 시스템 부하를 줄였습니다.

## 4. 실시간 인기글 선정을 위한 비동기 이벤트 스트리밍 (Kafka)

### 문제 상황: 자정마다 몰리는 대용량 배치(Batch) 연산 부하
*   **원인:** 매일 오전 1시마다 전날 생성된 모든 게시글을 전수 순회하여 **점수(좋아요 수x3 + 댓글 수x2 + 조회수x1)**를 계산하여 상위 10건의 인기글을 추출하는 전통적 배치 방식을 채택했습니다.
*   **병목:** 데이터가 수백~수천만 건으로 급증하자 배치 성능이 1시간을 초과하여 오전 1시 약속된 시간에 업데이트가 불가능해졌으며, 점수 합산 데이터를 얻기 위해 타 마이크로서비스(댓글, 좋아요 등)로 자정 직후 무수히 많은 단건 동기 API 쿼리가 쏟아져 전체 서비스들이 연쇄적으로 장애를 입었습니다.

```text
[인기글 서비스] ──(자정 대규모 API 호출 요청)──► [게시글/댓글/좋아요 서비스] ──► (DB 과부하 및 타임아웃 장애 유발)
```

### 해결 단계 1: 실시간 이벤트 기반 아키텍처(EDA) 도입
*   **해결:** 한 번에 부하가 몰리는 배치(Batch) 처리 대신, 데이터 흐름을 연속으로 처리하는 **실시간 스트림 처리(Stream Processing)** 방식으로 전환했습니다.
*   **구조:** 각 서비스에서 생성/수정/삭제 이벤트가 발생하면 즉시 Apache Kafka의 각 전용 토픽(`kuke-board-*`)으로 이벤트를 전송(Producer)합니다.
*   인기글 서비스는 `hot article Consumer Group`을 생성해 카프카의 실시간 파티션을 병렬 구독(Consumer)하며 유입되는 이벤트를 점수로 비동기 가공하기 시작합니다.

### 해결 단계 2: Redis Sorted Set(ZSET)을 활용한 점수 순위 집계
*   **구조:** 굳이 매번 12M 건을 정렬할 필요 없이, 각 게시글ID가 생성/수정될 때마다 계산된 수치를 **Redis의 Sorted Set (ZSET) 자료구조**에 실시간 업데이트(ZADD)합니다.
    *   **ZSET 키 구조:** `key = yyyyMMdd` (날짜별 분리).
    *   **데이터:** `member = article_id`, `score = 실시간 점수`.
*   **결과:** ZSET 자료구조가 내부적으로 정렬 상태를 유지하므로, 오전 1시에는 별도의 계산 쿼리 없이 **Redis ZSET에서 상위 10건(O(log N + M))을 조회해 표시**하면 됩니다.

### 해결 단계 3: 이중 쓰기 일관성 보장을 위한 트랜잭셔널 아웃박스(Transactional Outbox) 패턴
*   **문제:** 로컬 비즈니스 DB 저장과 카프카 이벤트 발행이 이중 쓰기(Dual-Write) 구조로 연속 호출되면, 카프카 전송 실패 시 DB 상태와 메시지 큐 간 데이터 일관성이 깨질 수 있습니다.
*   **해결:** RDB의 단일 로컬 트랜잭션 범위 내에서 비즈니스 데이터 수정과 동시에 카프카로 내보낼 원시 이벤트 페이로드 정보를 `outbox` 테이블에 물리적으로 결합해 영속시켰습니다.
*   **동작 매커니즘:**
    1.  로컬 트랜잭션 정상 완료 시, 비동기 이벤트 전달 기능과 함께 `outbox` 테이블에 적재됩니다.
    2.  `outbox` 전용 **Message Relay** 모듈이 10초 주기로 전송에 실패한 유실 이벤트(`created_at < 현재시간 - 10초`)들을 안정적으로 폴링(Polling)해 카프카로 재발행합니다.
    3.  카프카 브로커 적재가 Ack(`acks=all`, `min.insync.replicas=2`)로 확인되면, 아웃박스 테이블에서 해당 미전송 내역을 삭제(Delete)합니다.
    4.  **분산 Coordinator 제어:** 스케일 아웃된 다중 서버 환경에서 여러 메시지 릴레이가 동시에 아웃박스를 폴링하여 중복 메시지가 발행되는 비용을 막기 위해, Redis의 ZSET에 3초 주기로 생존 신고(ping)를 보내는 분산 코디네이터 구조를 구현하여 각 노드가 전담할 MySQL 샤드 범위를 독점 할당받게 조율했습니다.

## 5. 대규모 읽기 트래픽 대응을 위한 CQRS 및 캐시 최적화

### 문제 상황: 동기식 API 조인 병목 및 마이크로서비스 간 순환 참조
*   **원인:** 대규모 게시글 통합 조회 요청(게시글 본문 + 댓글 수 + 좋아요 수 + 조회수 일괄 조회)이 들어올 때마다 단일 서비스가 다른 3개의 물리 마이크로서비스로 동기 API 호출을 날려 데이터를 머지해왔습니다.
*   **병목:** 네트워크 지연이 누적되어 읽기 API 처리 시간이 수초 대로 치솟았으며, 데이터를 서로 검증하려는 과정에서 각 물리 마이크로서비스 간 **양방향 순환 참조 의존성이 강하게 발생**해 한 서비스 장애가 전사 시스템 셧다운으로 직결되었습니다.

### 해결 단계 1: CQRS(Command Query Responsibility Segregation) 도입
*   **해결:** 쓰기(Command)와 조회(Query) 목적의 애플리케이션 및 저장소 계층을 분리하는 **CQRS 기법**을 도입했습니다.
*   **구조:** 조회를 전문으로 담당하는 **`article-read` (게시글 조회 서비스)**를 독자적으로 구축하고, 여기에 단독 캐시 저장소인 Redis를 맵핑했습니다.
*   **비정규화 Query Model:** 게시글, 댓글 수, 좋아요 수를 하나로 합친 전용 비정규화 데이터 모델인 `Article Query Model`을 만들고, 기존 서비스가 발행한 카프카 이벤트를 실시간으로 컨슘해 해당 모델을 Redis 캐시에 미리 구성합니다.

### 해결 단계 2: 캐시 스탬피드(Cache Stampede) 차단을 위한 Request Collapsing 설계
*   **추가 문제:** 읽기 성능은 크게 향상되었으나, 실시간 읽기 트래픽이 초당 수만 건에 달할 때 **Redis에 캐시된 최신 Query Model이 만료(TTL)되는 순간 수많은 쓰레드에서 cache miss가 동시에 발생하고, 백엔드 원본 DB로 조회 요청이 몰려 서버 장애를 일으키는 캐시 스탬피드 현상**이 발생했습니다.

```text
[캐시 만료 시점] ──► [수천 개의 동시 요청 cache miss] ──► [동시 원본 MySQL 집중 쿼리] ──► [DB 다운 장애]
```

*   **근본 해결 (Request Collapsing & Logical/Physical TTL 분리):**
    *   **만료 시간 이원화:** 데이터의 실제 삭제 시점인 **Physical TTL**은 15초로 설정하고, 갱신이 필요하다고 가상 선언하는 **Logical TTL**은 10초로 짧게 이원화해 가져갑니다.
    *   **동작 로직:**
        1.  10초(Logical TTL)가 지나 logical cache miss가 발생하면, 최초 진입한 쓰레드 하나만 Redis `setIfAbsent`로 **"캐시 갱신 전용 분산 락"**을 획득합니다.
        2.  락 획득에 성공한 단 하나의 쓰레드만이 무거운 원본 데이터 서버에 접근해 캐시를 최신 상태로 갱신하여 덮어씁니다.
        3.  락 획득에 실패한 나머지 요청 쓰레드는 블로킹하지 않고, Physical TTL(15초) 내에 남아 있는 **이전 캐시 데이터를 제공받아(Stale-while-revalidate) 바로 응답**합니다.
    *   **결과:** 원본 데이터베이스로 향하던 중복 요청을 1회의 쿼리로 줄여 DB 부하를 낮췄습니다.
